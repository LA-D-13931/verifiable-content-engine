# 静态内容校验适配器（领域二）

引擎的**第二个领域**。领域一处理交互任务判题（用户在参数空间里的操作），
本适配器处理**静态内容一致性**（HTML 文档之间的关系：链接、锚点、标签配平、结构规范）。

两者共用同一形状：

```
一条声明式规则  →  一个可判定的检查  →  返回 { pass, reason, certificate }
```

---

## 一、两个文件，两种迁移深度（**这个区别必须说清楚**）

本目录下的五项检查，迁移深度**不一样**：

| 检查 | 文件 | 迁移深度 |
|---|---|---|
| 标签配平 | `checks.py` | **规则层** —— 声明式，一条规则一个函数 |
| 站内链接可达 | `checks.py` | **规则层** |
| 页内锚点存在 | `checks.py` | **规则层** |
| 内容卫生 | `checks.py` | **规则层** |
| 结构 / 例题 / 双语统计 | `checks_structure.py` | **报告层** —— 委托原脚本执行，只解析其结论 |

**「接进报告层」不等于「已迁移到规则层」。** 后者才是真正的引擎化；
前者只是把原脚本的输出纳入了统一报告。

`checks_structure.py` 之所以采用委托方式，是因为原脚本的
`check_file` / `check_section` / `check_question` 共约 230 行，
做的是「从 HTML 里按正则切出小节、例题、测验」，规则密集且互相牵连。
本项目的既定纪律是**不重写已验证的资产**（重写会把已验证的东西变回未验证状态，
主站 `.git` 那次事故就是这个教训）。

**后续工作**：把原脚本的三个解析函数逐个搬进 `checks.py`，
每搬一个做一次差分对照。**本次到此为止，不假装已经完成。**

## 二、怎么用

```bash
# 统一报告（人看）
python3 verify.py <站点目录>

# 机器可读
python3 verify.py <站点目录> --json
```

对主站只读快照跑：

```bash
python3 engine-core/adapters/static-content/verify.py \
        01_活工程/线代_两站对照/snapshot
```

## 三、为什么校验的是「快照」而不是主站

迁移期间要反复跑「原脚本」与「适配器」做差分对照。如果直接在主站上跑，
一旦某个工具带写入行为（哪怕只是 Bug），主站就被改了——
而「主站未被改动」是本项目唯一能自证清白的证据。

快照由 `apps/linalg-lab/tools/gen-snapshot.py` 生成：
只复制主站文件清单里登记的 432 个文件，**不软链接**
（软链接下写入会穿透回主站，复制则天然隔离）。

## 四、迁移纪律

> **只改组织方式，不改判定结论。**

每一步迁移都要证明：在**同一批文件**上，原脚本与适配器对同一项检查
给出**一致的结论与一致的统计量**。工具：
`apps/linalg-lab/tools/verify-static-adapter.py`。

当前差分对照结果（全部一致）：

| 项 | 原脚本 | 适配器 |
|---|---|---|
| 页面数 | 25 | 25 |
| 站内链接 | 719 条 / 失效 0 | 719 条 / 失效 0 |
| 失效锚点 | 0 | 0 |
| 卫生问题 | 0 | 0 |
| 小节 / 例题 / 测验卷 / 测验题 / 讲评 | 82 / 358 / 84 / 664 / 84 | 同 |

## 五、相对九套独立脚本的改进

| | 原脚本（九套各写各的） | 本适配器 |
|---|---|---|
| 输出格式 | 九种不同格式 | **统一结论行** |
| 失败信息 | 位置 + 现象 | 位置 + 现象 + **原因 + 证书** |
| 通过时 | 只写「通过」 | **给出统计量**（能看出检查真的跑了） |
| 加一项检查 | 再写一个脚本 | 在 `CHECKS` 表加一行（规则层部分） |

最后一条是「引擎化」与「多写一个脚本」的实质区别。

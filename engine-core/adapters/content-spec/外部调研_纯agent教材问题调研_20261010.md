## 类别一：技术实现问题（渲染、图表、交互、打包、性能、路由、状态）

### 1.1 公式渲染失败：AI 生成 KaTeX 表达式超出支持子集（严重：高，频率：常见）
- **问题描述**：Agent 在生成数学内容时，常使用 KaTeX 不支持的 TeX 命令或宏包语法，导致渲染报错。
- **典型表现**：Chat/Browser 中显示「KaTeX parse error」工具提示；报错后大段内容退化为红色未渲染原始文本，夹杂残留的 LaTeX、Markdown、表格 pipe，整段难以阅读。典型报错为 `ParseError: KaTeX parse error: Can't use function '\l' in math mode`。相关案例见 Cursor 社区 Bug 报告《Chat: KaTeX parse error breaks markdown/math rendering》。
- **影响**：核心教学内容是数学教材的命脉，渲染失败直接导致内容不可读、不可用，是最致命的呈现层问题。
- **可能原因**：KaTeX 只支持 LaTeX 的一个子集；Agent 语料中混杂了完整 LaTeX / MathJax / 学术模板宏（`\l`、`array`、`aligned` 边界、长除式等）。KaTeX 社区已就此展开讨论——Issue #4116《llms.txt》提议为 Agent 提供「Supported Functions」权威清单，以让 AI 知道哪些能渲染、哪些不能；但维护者认为收益有限。[cite:28625d68-2][cite:28625d68-1]
- **现有讨论/方案**：①为 Agent 提供 KaTeX 支持命令的白名单（llms.txt 思路）；②渲染失败时优雅降级为纯文本/错误占位，而非让整段变红；③Evelyn Learning 博客指出 KaTeX 学习门槛高、像「写代码再渲染」，且不同渲染器对整行/单行代码的期望不同、部分排版（如长除法）会对齐错误。[cite:28625d68-4]

### 1.2 MathJax 与 KaTeX 混用 / 语法兼容不一致（严重：中，频率：偶发）
- **问题描述**：教材内容可能源自不同渲染引擎（KaTeX 与 MathJax），两者对同一 LaTeX 表达式支持度不同，导致「某处正常、某处报错」。
- **典型表现**：同一公式在在线预览正常、导出 PDF 或切换到桌面端后报错。
- **影响**：跨形态（网页/PDF/桌面）一致性差，增加维护成本。
- **可能原因**：Agent 未统一约定渲染引擎与语法子集；导出链路用了另一套渲染器。
- **现有讨论/方案**：Evelyn Learning《Challenges in writing Math for the web》指出不同渲染 Agent 对同一输入期待不同（如整行 vs 多行），且某些应用无即时预览，难以就地修正。[cite:28625d68-4]

### 1.3 图表生成困难：LLM 直接产出 ECharts/D3 配置易出错（严重：高，频率：常见）
- **问题描述**：让 Agent「输入数据 → 直接返回 ECharts option」效果差，常出现值域、轴、系列配置错误。
- **典型表现**：图表空白、坐标错、图例缺失、配置项非法导致整图不渲染。
- **影响**：教材中的可视化（统计图、几何图、关系图）失效或失真。
- **可能原因**：把整段时序/数据塞给 LLM 让它「当场写 option」，超出其可靠范围；叠加 Markdown 包裹（三重反引号）导致解析脆弱。
- **现有讨论/方案**：实践者建议让 Agent「写能执行查询并返回 option 的代码」而非直接吐 option；把图表 ID、查询生成、渲染拆成独立 Agent 逐步演进；增加校验层、用 SSE 流式输出提升体验；用代码执行代替「全量工具塞进提示」。

### 1.4 交互组件生成质量不稳定（严重：中，频率：常见）
- **问题描述**：Agent 生成的滑块、拖拽、滚动翻页、选择题作答、代码执行等交互组件，常出现事件绑定错误、状态不同步、组件间冲突。[cite:f3360316-5]
- **典型表现**：交互无响应、作答无法提交、拖拽复位异常。
- **影响**：教材「交互」这一核心卖点失效。
- **可能原因**：多 Agent 各自生成的组件缺乏统一状态契约；无校验层的格式不匹配（一个 Agent 产 YAML、另一个期待 JSON）。
- **现有讨论/方案**：给多 Agent 系统补上「JSON Schema 化契约、显式所有权、自动约束校验」。[cite:f3360316-2]

### 1.5 跨平台打包与签名（严重：中，频率：常见）
- **问题描述**：把交互式教材打包为桌面应用（Electron/Tauri 等）以及生成安装包时，遇到签名/公证/更新机制问题。
- **典型表现**：macOS 需 Apple Developer 证书并做 notarize（年度费用 + 配置复杂）；Windows 需另购证书；打包体积大（Electron 50–150MB+）；自动更新管道与打包器需针对框架重写。
- **影响**：分发受阻、安装包无法被信任、更新体验差；桌面形态是教材的重要发布形态之一。
- **可能原因**：平台原生签名/公证是硬性流程；Electron/Tauri 的打包、更新插件、CI 配置不通用，迁移需重写。[cite:50ca5566-1][cite:50ca5566-3]
- **现有讨论/方案**：需要「像素级一致 + 成熟签名/自动更新工具链」时选 Electron；追求体积与内存则用 Tauri（但 WebView 在部分 Linux/Wayland 有兼容问题，托盘图标不出现等）。[cite:50ca5566-1][cite:50ca5566-3][cite:50ca5566-4]（bun/Electrobun 等替代方案尚在实验期。[cite:50ca5566-5]）

### 1.6 性能：DOM 节点过多 / 虚拟滚动 / 长文档渲染（严重：中，频率：常见）
- **问题描述**：长篇教材页一次性渲染海量节点导致滚动卡顿。浏览器对大 DOM 树的布局、样式计算、内存开销随节点数急剧恶化。[cite:760f62e8-2]
- **典型表现**：页面切换/滚动顿挫、长时间会话内存上涨、冻结或崩溃。[cite:760f62e8-2]
- **影响**：教材体量大（章节多、公式图多），滚动体验差直接劝退。
- **可能原因**：未使用虚拟滚动/懒加载；长列表全量渲染。
- **现有讨论/方案**：虚拟滚动只渲染视口内元素 + 缓冲区，固定高度实现简单、动态高度需测量缓存；分页或懒加载对短列表够用。虚拟滚动本身在重渲染视口时也可能有性能问题。[cite:760f62e8-2][cite:760f62e8-3][cite:760f62e8-5]

### 1.7 SPA 路由与导航（严重：中，频率：常见）
- **问题描述**：用 SPA 组织教材章节页面时，路由/侧边栏链接处理不当。
- **典型表现**：侧边栏链接是标准 `<a>` 未接入路由器，点击触发整页刷新；URL 无法书签/分享；浏览器前进后退失效。[cite:0ff234f9-1][cite:0ff234f9-3]
- **影响**：章节切换体验差、无法分享特定章节位置。
- **可能原因**：未用客户端路由统一管理；页面状态与路由未解耦。
- **现有讨论/方案**：接入 React Router 等客户端路由，页面视为顶层应用状态而非独立文档。[cite:0ff234f9-1]

### 1.8 SPA 可访问性（严重：中，频率：中）
- **问题描述**：SPA 客户端路由导致屏幕阅读器无法播报路由变化、焦点丢失、动态内容不播报、浏览器历史/标准模式破坏。[cite:0ff234f9-4]
- **典型表现**：无障碍用户无法感知页面切换，keyboard 导航失灵。
- **影响**：教材应惠及更广人群，可访问性缺失是内容质量外的隐性缺陷。
- **现有讨论/方案**：路由切换时显式播报、管理焦点、动态内容用 ARIA live regions、测试用屏幕阅读器贯穿开发。[cite:0ff234f9-4]

### 1.9 状态管理（严重：中，频率：中）
- **问题描述**：章节进度、侧边栏开关、已读标记等跨页面状态管理混乱。
- **典型表现**：不同 Agent 各自用 useState，状态不同步（错误示例 `window is not defined`、localStorage 混用）；阅读进度丢失。
- **可能原因**：无单一数据源/无统一状态层。
- **现有讨论/方案**：用路由 loader + 服务端/持久化状态（如 cookie 存储侧边栏偏好）统一管理。[cite:0ff234f9-5]

## 类别二：内容生成问题（正确性、逻辑、题号匹配、衔接、难度递进、幻觉、重复、遗漏）

### 2.1 数学正确性：基本计算/推理错误（严重：高，频率：常见）
- **问题描述**：AI 生成的数学题目与解答常出现计算错误或错误逻辑。WSJ 报道 Khan Academy 的 AI 导师 Khanmigo 在基本计算上频频出错；模型不遵循一致规则（不像计算器），并对同一问题给出矛盾答案。[cite:b2175d6c-1]
- **典型表现**：答案错误、过程自相矛盾、同一问题多次提问结果不同。
- **影响**：教材核心正确性受损，误导学习者。
- **可能原因**：LLM 是「基于文本预测」而非「规则计算」；多步推理链易断。
- **现有讨论/方案**：Khan Academy 把数值问题导向计算器、新增「数学 agent（计算器）」校验计算；但引入计算校验会增加延迟——他们曾「先移除数学 agent → 数学错误翻倍 → 立即回滚」，做过 A/B 权衡。此外用「错误分析」教学法让学澄清为何错。[cite:b2175d6c-2][cite:b2175d6c-1]

### 2.2 幻觉与知识填充（严重：高，频率：常见）
- **问题描述**：模型在知识缺口处用「貌似可信」的文本填充，这种伪造最难检测（读起来同样自信）。引用层面：一项分析 115 条 ChatGPT 引用，47% 为编造、46% 引用真实文献但提取错误、仅 7% 正确。参考文献被整体编造的现象普遍。[cite:63f12ce6-3]
- **典型表现**：教材出现不存在的「引文/定理/参考文献」、错误数据、杜撰术语或日期。
- **影响**：教学内容准确性被系统性破坏；教学场景尤需「不输出事实错误」的硬约束。[cite:63f12ce6-2]
- **现有讨论/方案**：①人类审核 + 反馈回路（teacher-in-the-loop）捕获并纠正；②给 AI 明确「不输出未经证实内容」的准则；③多轮对话/自反思（self-correcting）降低幻觉；④交叉核对同行评审文献。[cite:63f12ce6-2][cite:1b7d82a9-2]

### 2.3 语言错配与重复（严重：中，频率：常见）
- **问题描述**：机器翻译/多语种教材中，出现「语言错配」（目标中文却输出英文）与「重复子串」（一段内容重复生成）。[cite:0c39c823-1]
- **典型表现**：中英对照教材某节为英文、某段文字重复、表达生硬。
- **影响**：双语教学教材质量受损。
- **可能原因**：LLM 对目标语言与重复模式的约束失效。
- **现有讨论/方案**：构造 `y=[ynorm, yrepe, yrepe, yrest]` 分解以定位最小重复单元；需在翻译/生成层面专项处理。[cite:0c39c823-1]

### 2.4 题号与题目/答案不匹配（严重：高，频率：常见）
- **问题描述**：练习题的题号、题干、答案、解析之间编号错位或对应错误。
- **典型表现**：第 3 题答案写的是第 5 题的解析；导航/目录题号与正文不符。
- **影响**：高严重度——答案错位在教学场景几乎等同于「答案错误」。
- **可能原因**：分块生成时上下文信息丢失；多 Agent 各自生成题目与解答却无统一编号契约。[cite:f3360316-1][cite:f3360316-2]
- **现有讨论/方案**：统一「单一数据源」，题目与答案在结构化数据里同题号绑定；把编号视为需约束校验的契约字段。[cite:f3360316-2]

### 2.5 难度递进 / 知识点衔接不严谨（严重：中，频率：中）
- **问题描述**：教材在章节间的知识铺垫、难度梯度上不连贯；AI 生成的题目「认知深度」参差。相关研究《From Memorization to Creation: Evaluating the Cognitive Depth of LLM-Generated Educational Questions》专门评估 LLM 生成题目的认知层级。[cite:0f3cedd6-5]
- **典型表现**：某一章突然跳难度、前置知识未讲清、题目与教学目标脱节；生成内容「不真实、缺乏与真实生活的关联、增加学生阅读负担」。[cite:28625d68-5]
- **影响**：影响学习路径的合理性。
- **可能原因**：缺乏整体教学大纲一致的约束；评分者（如 Flesch–Kincaid 阅读等级）未贯穿生成与修正。
- **现有讨论/方案**：多 Agent 框架中引入「验收 Agent（validator）→ 修正 Agent（refinement）」，以保守原数学结构、目标话题与年级阅读等级的方式，对「贴近真实、匹配原水平、数学一致」四约束迭代修正。[cite:28625d68-5]

### 2.6 内容重复、遗漏、不完整（严重：中，频率：常见）
- **问题描述**：长篇批量生成时内容重复（同一知识点多章反复）、遗漏（某目录章节无内容）。上下文溢出是常见触发因素——长会话/长文档中模型「忘记前文」。[cite:0c39c823-3]
- **典型表现**：章节去重失效、目录与正文对不上、某个主题被漏写。
- **影响**：教材结构失衡、体量失真。
- **可能原因**：长上下文未压实（compaction）、分块生成缺乏全局清单。
- **现有讨论/方案**：会话压缩/总结保留全局大纲；把「已覆盖主题清单」作为约束喂给后续 Agent，避免重复与遗漏。[cite:0c39c823-3]

### 2.7 逻辑严谨性与「口语化错误」（严重：中，频率：中）
- **问题描述**：学术/教育内容中出现语气、措辞不当，或直觉性但反常识的推理错误。人类因模型逻辑偏离常理而较易察觉某些错误。[cite:63f12ce6-4]
- **典型表现**：语气像「聊天机器人」而非教材、论证不严谨、结论跳跃。
- **影响**：影响教材可信度与教学法质量。
- **现有讨论/方案**：通过多轮对话让错误暴露；配以人类审核。[cite:63f12ce6-4]

## 类别三：交互设计问题

### 3.1 导航/侧边栏/底部导航体验差（严重：中，频率：常见）
- **问题描述**：章节导航（侧边栏、底部导航、滑动翻页）在长教材中组织混乱，链接触发整页刷新、无法记录阅读位置。[cite:0ff234f9-1]
- **典型表现**：翻页卡顿、侧边栏与滚动位置不同步、点击跳转整页加载。
- **影响**：阅读连贯性差。
- **可能原因**：导航与路由/状态未打通。
- **现有讨论/方案**：客户端路由 + 持久化阅读位置。[cite:0ff234f9-1][cite:0ff234f9-5]

### 3.2 交互组件（拖拽/弹窗/作答）体验参差（严重：中，频率：中）
- **问题描述**：Agent 生成的弹窗、拖拽排序、作答弹层等交互细节粗糙、状态不同步。
- **影响**：降低「交互式」卖点信服力。
- **可能原因**：多组件缺乏统一状态契约；格式不匹配无校验。[cite:f3360316-2]

### 3.3 响应式适配（严重：中，频率：常见）
- **问题描述**：教材需同时适配桌面（侧边栏+宽阅读区）与移动端（底部导航+窄屏），响应式布局未妥善处理。[cite:0ff234f9-2]
- **典型表现**：小屏每屏内容过载、图表/公式溢出、侧边栏挤压正文。
- **影响**：移动端学习场景（通勤、碎片阅读）体验差。
- **可能原因**：未做断点与栅格、适配依赖固定宽度。

### 3.4 可访问性与键盘导航（严重：中，频率：中）
- **问题描述**：Spa 交互组件缺少键盘可达与 ARIA 支持，见 1.8。[cite:0ff234f9-4]

## 类别四：工程化问题（代码组织、组件复用、单一数据源、版本控制、构建、部署）

### 4.1 Agent 生成的代码组织差 / 越界改动（严重：中，频率：常见）
- **问题描述**：Agent 在不理解上下文时的常见病：误用工具（malform 调用删掉整个文件）；不读文件而「猜」并写出「漂亮但无用」的代码（有时删空后用优美废话重写）；进行不必要的越界编辑。[cite:e3ec0694-5]
- **典型表现**：改动了无关文件、违规的「脚手架」、重复实现而非复用既有组件。
- **影响**：组件复用率低、代码膨胀、引入回归。
- **可能原因**：缺少「先读再做」的约束与审查。
- **现有讨论/方案**：明确「只改被指示的步骤」「遇到问题或发现即停止报告」，以约束越界与猜测。[cite:e3ec0694-5]

### 4.2 单一数据源缺失 / 组件复用率低（严重：中，频率：常见）
- **问题描述**：内容（正文、题、答案、图表数据）与「呈现组件」未分离或未复用；答案与题目、目录与内容各自维护。
- **影响**：修改一处要同步多处，易错；多 Agent 并行写同一位置产生竞态（conflicting resource ownership）。[cite:f3360316-1]
- **现有讨论/方案**：以结构化内容（JSON）作为单一数据源，组件消费之；显式资源所有权。[cite:f3360316-2]

### 4.3 构建/部署/版本控制（严重：中，频率：中）
- **问题描述**：桌面化后构建与自动更新管道复杂；Agent 在版本控制细节（只改被指示步骤、明确分支）上易失控。[cite:50ca5566-3][cite:e3ec0694-5]

## 类别五：协作与维护（多 Agent 协作、人工审核、错误修复、回归、文档）

### 5.1 多 Agent 协调失败（严重：高，频率：常见）
- **问题描述**：多 Agent 系统在 41%–86.7% 的故障率下运行，根因多是「协调/规范」而非模型质量。典型失败模式：上下文坍缩（一个 agent 输出超过另一个的窗口，关键状态静默丢弃）、格式不匹配（A 产 YAML、B 期待 JSON、中间无校验）、资源所有权冲突（两个 agent 写同一位置）、自然语言歧义（「处理订单」在不同上下文含义不同）。规范问题 42%、agent 间不对齐 37%、任务校验不足 21%；规范与协调问题占生产故障约 79%。[cite:f3360316-1][cite:f3360316-2][cite:f3360316-4]
- **典型表现**：重复劳动、角色漂移、循环争论、任务无归属、级联超时。
- **影响**：开发教材的 Agent 流水线不稳定，需大量人工兜底。
- **可能原因**：把规范当「散文说明」而非「API 契约」；Agent 无法在运行时澄清，每个歧义成决策点。[cite:f3360316-2]
- **现有讨论/方案**：把规范写成 JSON Schema 契约、显式所有权、自动约束校验；由于每次交接追加 100–500ms 序列/网络延迟、token 随重建上下文复合，存在「协调开销饱和」阈值——超过后并行优势消失，需权衡是否值得多 Agent 化。[cite:f3360316-1]

### 5.2 人工审核（Human-in-the-loop）不足（严重：高，频率：常见）
- **问题描述**：仅靠 AI 生成、缺人工校验会传播错误信息。多 Agent 与教育内容需 teacher-in-the-loop / HITL 回路。研究指出自反思 AI 导师（译者自校）、教师参与验证是缓解幻觉/错误的方向。[cite:63f12ce6-2][cite:1b7d82a9-2]
- **典型表现**：错误内容直接进入教材；审核开销大、难以规模化（Human review at scale）。[cite:1b7d82a9-3]
- **现有讨论/方案**：HITL 框架（反馈回路）、预标注（AI 先预测再交人工验证，提高人效）、「何时需要人类审核」的建议器。[cite:1b7d82a9-1][cite:1b7d82a9-3]

### 5.3 回归测试与错误修复（严重：中，频率：中）
- **问题描述**：Agent 修复一个错误时可能引入新错误；缺乏对内容/渲染快照的回归测试。
- **影响**：教材质量不稳定、迭代返工。
- **现有讨论/方案**：把「先复现后修复」「遇到问题即停止」的纪律融入 Agent 指令。[cite:e3ec0694-5]

### 5.4 文档与版本混乱（严重：低，频率：中）
- **问题描述**：教材迭代中章节/答案/解释版本漂移，缺乏清晰变更记录与归属。

## 类别六：性能问题

### 6.1 启动速度（严重：中，频率：常见）
- **问题描述**：桌面应用（Electron 大体积）与重前端加载慢；教学场景期望快速打开。
- **影响**：体验差，尤其需频繁进出场景。
- **现有讨论/方案**：Electron 50–150MB+、Tauri 体积小一个量级、但 WebView 渲染差异需兼容。[cite:50ca5566-3][cite:50ca5566-2]

### 6.2 页面切换卡顿 / DOM 节点过多 / 内存泄漏（严重：中，频率：常见）
- **问题描述**：长篇教材全量渲染 + 长会话内存累积，见 1.6。[cite:760f62e8-2]
- **现有讨论/方案**：虚拟滚动、懒加载、固定高度简化、动态高度需测量缓存。[cite:760f62e8-2][cite:760f62e8-3]

## 类别七：成本与资源

### 7.1 Agent 级任务的 token 消耗激增（严重：高，频率：常见）
- **问题描述**：Agent 编码类任务 token 消耗比聊天/推理高约 1000×，且**输入 token 成为成本主导**（每轮把整个轨迹重新回喂给模型）。同一任务 token 用量可差 30×，准确率往往在中等成本处达峰，超额支出多为冗余探索。[cite:026e596b-5]
- **典型表现**：写一章教材反复重构上下文导致 token 爆炸、预算失控。
- **影响**：长教材（几十万字）成本昂贵且难预测。
- **现有讨论/方案**：不要为「每步逻辑」都付 LLM 调用；只在 LLM 独特的决策/生成处付费，之后让既定 plan 用常规代码跑，避开每步 token；只加载需要的工具；Anthropic 案例中「工具全量塞提示」约 15 万 token → 「代码执行」约 2 千 token（降 98.7%）。[cite:026e596b-1]

### 7.2 无上限的 token 支出与「隐形」成本（严重：高，频率：常见）
- **问题描述**：Agent 可自主扩大范围、进入递归循环、过度查询、每轮重发全量历史以维持上下文，成本无天花板。token 消耗对财务「不可见」——某医疗企业半年 1 万亿 token、超 600 万美元非计划成本。[cite:026e596b-4]
- **典型表现**：越跑越贵、无法提前预估；生成教材的计划不断自我膨胀。
- **现有讨论/方案**：任务分层路由（60–70% 的简单任务用 1/10 成本的小模型无明显质量差）、prompt 缓存、子 agent 超时、夜间降档模型；案例中 76% 成本降幅。[cite:026e596b-3][cite:026e596b-4]

### 7.3 算力 / 生成时间（严重：中，频率：常见）
- **问题描述**：长教材生成耗时长，LLM 往返延迟累积；教育迭代需即时反馈。
- **现有讨论/方案**：结论存在「协调开销饱和」——并行化收益被交接延迟/重建上下文抵消。[cite:f3360316-1]

## 类别八：法律与伦理

### 8.1 版权归属不确定（严重：中，频率：常见）
- **问题描述**：完全由 AI 生成、无充分人类创作性参与的作品，依 US Copyright Office 与法院判例通常**不可获版权**，可能落入公共领域。教材若几乎纯 Agent 生成，作者可能不拥有版权；部分出版方已在合同中加入约束 AI 生成的条款。[cite:d8c2fbab-5][cite:d8c2fbab-3]
- **典型表现**：分享/再版教材时存在「权利不清」困境，即「法律不确定的瘫痪」——教育者害怕作错误的合法决定而止步。[cite:d8c2fbab-3]
- **现有讨论/方案**：明确「有意义的人类贡献」、界定作者归属；机构在课程大纲/研究协议中写明 AI 使用与所有权标准。[cite:d8c2fbab-5]

### 8.2 学术诚信 / AI 剽窃（严重：中，频率：常见）
- **问题描述**：未披露的 AI 生成内容可能构成剽窃/学术不端；需要「具体披露」（说明哪部分来自 AI、附链接），而不仅是笼统「我用过 AI」。[cite:d8c2fbab-2][cite:d8c2fbab-4]
- **典型表现**：教材未标注 AI 来源、学生提交 AI 作品当作原创。
- **影响**：信任与教育伦理问题。
- **现有讨论/方案**：设定明确的课堂/机构 AI 使用政策、鼓励具体披露、教职工具备裁定 AI 使用程度的自主权。[cite:d8c2fbab-2]

### 8.3 内容准确性与隐私（严重：中，频率：中）
- **问题描述**：内容准确性（见类别二）及其余痛点是教育场景伦理核心；此外敏感数据、学生作品本身也受版权保护，选 AI 工具需保证数据不予留存或再训练。[cite:d8c2fbab-1]
- **影响**：若工具将学习数据用于训练或因数据泄露，责任重大。
- **现有讨论/方案**：选择有强数据安全实践的工具、保证数据不被存储或复用为训练语料；将版权与数据保护纳入数字素养与学术诚信政策。[cite:d8c2fbab-1]

## 检索局限性与后续建议

1. **资料局限**：本次调研以英文公开社区（GitHub、Stack Overflow、Reddit、arXiv、Medium、Google Developers、教育行业媒体）为主。中文社区（知乎、掘金、CSDN、V2EX、微信公众号）的一手开发帖因检索覆盖不足未能系统采集，相关中文语境条目为归纳推断，建议补充对中文社区的关键词抓取以「待验证」核验。
2. **领域定义局限**：检索命中多为「AI Agent 开发通用问题」「LLM 教育内容生成」两类文献交集，**「纯 Agent 端到端编写交互式教材」这一细分领域鲜有专门的系统化研究/实证论文**，因此此处结论多由相邻领域（多 Agent 系统、LLM 教育内容生成、前端交互教材工程）迁移归纳而来，属「合成性结论」，非该细分领域的专属实证。
3. **不提供教学内容**：本报告仅汇总问题与可能原因/参考方案，不含具体教学大纲、文案或题目。
4. **建议进一步定点调研**：①KaTeX/Canvas/WebG 渲染在长教材的实测性能基准；②多 Agent 生成教材的实际 token/成本测算；③可访问性（无障碍）在教育教材中的专门标准；④国内交互教材（慕课/数字教材）场景与政策合规。

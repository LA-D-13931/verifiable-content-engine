# 教材编写中的失败模式台账（含：能不能被引擎抓住）

**来源**：另一个真实项目（Stanford CS231n 教材 + 高数站）的复盘台账
`docs/高数站开发问题与要求总览.md`（57 条用户指正 + 6 条失败模式）、
`docs/界面组织与交互逻辑要求.md`（UI/交互母规范，含「改完必做自检」8 条与「明确禁止」12 条）、
`docs/交互式命题与批改规范.md`，以及本域首跑真实产物时自己抓到的缺陷。

**为什么放在引擎里**：这些不是"某个项目的经验"，而是**教材编写这一类工作反复踩的坑**。
引擎的价值不在"多一条规则"，而在**把病因变成可判定的不变量**——用户原话：
> 「我希望这个项目做出来不只是一个给 agent 的规范，而是能交给 agent 如何用他手上有的逻辑链和有的开发工具去发现和修正问题。」

所以本文件每条都记四件事：**病因 → 判据 → 状态（已进引擎／未做／只能靠人）→ 修法与验证**。

## 三、「改完必做自检」与「明确禁止」→ 直接可做的检查

### 3.1 UI 规范 §十三 的 8 条自检，逐条落到引擎

| 规范原条目 | 引擎怎么做 |
|---|---|
| 1 布局外溢、无横向滚动条 | 渲染量测（P5） |
| 2 对比度 ≥4.5:1（正文/链接/按钮 ≥7:1） | 委托项目已有脚本（Q13：站点特有且有成熟实现 → 委托） |
| 3 320px 窄屏不溢出 | 渲染量测（P5） |
| 4 **解压到全新目录再跑一遍**（源码目录会因构建顺序漏检） | 引擎的交付闸门已经是这个思路（补丁打到**干净副本**再验）；把"在干净副本上跑"固化成检查的前提 |
| 5 交互实测（拖动／收起／展开／**刷新后状态保持**／跨标签页） | 浏览器探针（复用引擎已有的 4 项浏览器自检 + 委托项目探针） |
| 6 锚点实测（落点准、不被拽回） | 浏览器探针 |
| 7 高亮实测（不闪动、不重叠、对得上） | 浏览器探针（含"同一时刻只一处"这种可断言的不变量） |
| 8 **判断"已修好"之前必须重新测量** | 写进每条检查的**验证字段**：处置卡必须给出可执行命令；"我改了代码"不算修好 |

### 3.2 §十四「明确禁止」的 12 条里，**静态就能判**的

这一批值得做成**一条声明式检查**（`forbidden-patterns`）：manifest 列出禁止模式 + 理由 + 修法，
产物里出现即报。它一次覆盖下面 6 条：

1. 同一选择器重复定义（后者覆盖前者 → 布局被拆）
2. 用已被变量化的十六进制色值当替换锚点（替换静默不生效）
3. 批量替换短色值（`#fff` 先匹配到 `#ffffff` → 产生非法值）
4. 整页开启平滑滚动
5. 给大区块加 `content-visibility: auto`
6. 折叠层标题写成"详见下文"
7. 静态写死导航结构（= 单一数据源那条，已被 `single-source` 覆盖）
8. 无条件把用户滚回锚点 / 同一时刻画两处背景胶囊 / 让"跟随系统"不可回到 → 需渲染层断言（P5）

### P1 落地记录（真实过程，含两个假阳性）

- **先测量再声明**，结果我的第一版探针在真实产物上给出两个**假阳性**——正是 M5 本人：
  ① 「非法色值」命中的是 HTML 实体 `&#42;`（JS 里表示 Markdown 的 `*`）：**子串伪装**；
  ② 「重复选择器」没按 at-rule 作用域分开统计（媒体查询/主题块里重复是合法的）。
  修判据后：非法色值 **0 命中**，禁止模式 **0 命中**。
- **然后抓到真东西**：`duplicate-selector` 在 **8 个独立页**上命中 `.cd` 同作用域重复定义
  （`:58` 在组合选择器里、`:61` 独立定义，后者覆盖前者的 padding/background）。
  这与站点自己的规范「同类选择器只允许出现一次」直接冲突 → 已登记 `duplicate-selector-cd`，等站主决定"合并"还是"声明为有意级联"。
- **失败时给的处置卡**含：结论 / 证据 / 缺陷所在 / 改法 / 泛化 / 验证命令（第六节的七字段）。
- **仍未覆盖的缺口（如实记）**：高数站的样式在**外部 CSS** 里（页面只有 `<link>`），
  所以 `duplicate-selector` 在那 12 个页面上报「不适用」——诚实的"不适用"，
  但要覆盖它需要声明 `style_sources` 并把 workspace 解析接进去。这是下一项。

**排序原则**：P1 最便宜且一次覆盖 6 条；P2 覆盖最致命的一类（静默丢内容）；P3/P4 治的是"编造"与"过度自信"；
P5 需要渲染层，最后做。

## 五、写进每条检查的"发现 → 定位 → 修 → 验证"

这是本域对用户那句原则的实现方式。每条检查失败时输出的**处置卡**必须含：

```
结论     —— 一句话说清"哪里、为什么错"
证据     —— 可复核的依据（逐项列出，不是一句"失败了"）
缺陷所在 —— 生成它的代码/数据位置（file:line），不是产物行号
照着谁改 —— 同仓库里已经做对的那一处（可照抄，不必自己设计）
改法     —— 具体到"改哪个文件的哪几行、加什么"
泛化     —— 这个判据还能往哪扩（教方法，不止修这一处）
验证     —— 一条可执行命令；**重新测量过才算修好**（§十三 第 8 条）
```

**"重新测量才算修好"这一条，本身就是从台账里学来的**：曾经对着未更新的缓存图宣布"已修好"。
所以处置卡的验证字段必须是**命令**，不是"请检查一下"。

## 六、这份台账自己的规矩

1. **每条都要能证伪**：写不成"改一个已知坏例、它必须变红"的条目，不许进第四节充数；
2. **症状会变、病因不变**：新增条目时先问"它属于 M1–M6 里的哪一条"——归不进去的，可能是个新病因，
   那才值得单独加检查；
3. **同一个问题第三次出现时**，该问的不是"再修一次"，而是"**这个功能还该不该存在**"
   （台账第十二节的原话；那一次用户的答案是：废掉图解）；
4. **本文件不记具体教学内容**，只记机制与判据。

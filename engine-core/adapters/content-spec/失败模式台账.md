# 教材编写中的失败模式台账（含：能不能被引擎抓住）

**来源**：另一个真实项目（Stanford CS231n 教材 + 高数站）的复盘台账
`docs/高数站开发问题与要求总览.md`（57 条用户指正 + 6 条失败模式）、
`docs/界面组织与交互逻辑要求.md`（UI/交互母规范，含「改完必做自检」8 条与「明确禁止」12 条）、
`docs/交互式命题与批改规范.md`，以及本域首跑真实产物时自己抓到的缺陷。

**为什么放在引擎里**：这些不是"某个项目的经验"，而是**教材编写这一类工作反复踩的坑**。
引擎的价值不在"多一条规则"，而在**把病因变成可判定的不变量**——用户原话：
> 「我希望这个项目做出来不只是一个给 agent 的规范，而是能交给 agent 如何用他手上有的逻辑链和有的开发工具去发现和修正问题。」

所以本文件每条都记四件事：**病因 → 判据 → 状态（已进引擎／未做／只能靠人）→ 修法与验证**。

## 状态列四值契约（六轮指令 §2.3）

```
状态列四值：未做 ｜ 部分 ｜ 已实现 ｜ 已废弃
判定规则：
  · 已实现 = 有代码 + 有反例 + 能被一条命令复现
  · 部分   = 有代码但覆盖面/生效条件不全（必须写明缺什么）
  · 未做   = 无代码
  · 已废弃 = 明确决定不做（必须写明理由）
```

**为什么先定契约再填**：本文件的"状态"列此前出现过两种不同的过期——
（a）**过时**（M6 写着"❌ 本批做"，实际已建成）、（b）**未更新**（P4 无状态，实际已实现）。
没有四值契约时，"已做/部分/未做"全靠手感，于是同一个格子会出现四方数字互不相同的局面
（突变体数：文档 11、开发 11、复审 9、真值 8）。
**填写者必须能回答"凭什么说它已实现"** —— 答案只能是上面那三件（代码 + 反例 + 一条命令）。

### 3.1 UI 规范 §十三 的 8 条自检，逐条落到引擎

| 规范原条目 | 引擎怎么做 |
|---|---|
| 1 布局外溢、无横向滚动条 | 渲染量测（P5） |
| 2 对比度 ≥4.5:1（正文/链接/按钮 ≥7:1） | 委托项目已有脚本（Q13：站点特有且有成熟实现 → 委托） |
| 3 320px 窄屏不溢出 | 渲染量测（P5） |
| 4 **解压到全新目录再跑一遍**（源码目录会因构建顺序漏检） | 引擎的交付闸门已经是这个思路（补丁打到**干净副本**再验）；把"在干净副本上跑"固化成检查的前提 |
| 5 交互实测（拖动／收起／展开／**刷新后状态保持**／跨标签页） | 浏览器探针（复用引擎已有的 4 项浏览器自检 + 委托项目探针） |
| 6 锚点实测（落点准、不被拽回） | 浏览器探针 |
| 7 高亮实测（不闪动、不重叠、对得上） | 浏览器探针（含"同一时刻只一处"这种可断言的不变量） |
| 8 **判断"已修好"之前必须重新测量** | 写进每条检查的**验证字段**：处置卡必须给出可执行命令；"我改了代码"不算修好 |

### 3.2 §十四「明确禁止」的 12 条里，**静态就能判**的

这一批值得做成**一条声明式检查**（`forbidden-patterns`）：manifest 列出禁止模式 + 理由 + 修法，
产物里出现即报。它一次覆盖下面 6 条：

1. 同一选择器重复定义（后者覆盖前者 → 布局被拆）
2. 用已被变量化的十六进制色值当替换锚点（替换静默不生效）
3. 批量替换短色值（`#fff` 先匹配到 `#ffffff` → 产生非法值）
4. 整页开启平滑滚动
5. 给大区块加 `content-visibility: auto`
6. 折叠层标题写成"详见下文"
7. 静态写死导航结构（= 单一数据源那条，已被 `single-source` 覆盖）
8. 无条件把用户滚回锚点 / 同一时刻画两处背景胶囊 / 让"跟随系统"不可回到 → 需渲染层断言（P5）

### 委托机制与 C1 落地记录（引擎底层第二批）

- **委托机制**（`checks_delegate.py`）：站点自有脚本按契约接入，三条硬约束写在代码里：
  **退出码即结论**、**必须声明 `read_only`**（未声明则**拒绝执行**——门禁里跑会写文件的脚本
  = 把检查变成破坏）、**必须声明 `timeout`**（卡住的脚本不能拖死整套门禁）。
  三态：脚本不在位 → 不适用；退出 0 → 通过（stdout 存进证书）；非 0 → 失败（把脚本自己的输出当证据）。
  **首个真实委托**：高数站 `tools/check-numbering.py`（中英编号一一对应、Property 残留 0），实跑退出码 0 ✓。
  机制自检覆盖四条走向：通过 / 失败 / **未声明只读被拒** / 缺失→不适用。
- **委托的审计与失败区分**（本次补）：`runner.py --delegates` 一条命令列出"门禁会替我执行哪些外部脚本"
  （脚本位置 / 是否声明只读 / 超时 / 期望），缺声明即标红；`--explain` 交出每条判据的逻辑链；
  `--json` 给机器消费。另外把**工具故障与内容缺陷分开**：脚本自己崩（Traceback / Node.js v / ModuleNotFoundError …）
  判「环境不足」，不当内容失败——否则就是拿工具故障去判内容红。真实委托已从 1 个扩到 8 个站点脚本，
  其中 `check-missing-math.py`（退出码 1）**首跑就抓到一个真缺陷**：多处「汉字与标点间有空格（公式疑被抽走）」。
- **C1 证据类型契约**：每条检查必须声明 `structural`/`render`/`human`/`external` 之一，
  **缺声明则门禁拒绝运行**（已反证：去掉一条声明 → 退出码 1）。
  `human` 类**不计入全绿**——它只能报"需人复核"，不能替人签字。当前 14 structural + 1 external。

### dup-block 重做记录（负结果 → 判据重设计 → 落地）

第一版判据"同页重复段落"在真实站点上量出 **12/12 页共 325 段"重复"**——逐条看**全是 `$$…$$`
公式段**；数学教材里公式复现是合法的（定理/证明/例题各出现一次很正常）。照此实现会假阳性 325 处，
所以当时**记为负结果、不实现**，并写下重做所需的四条条件。

重做（`checks_text.py`）：① 只认散文（含中文、无 `$` 与 `\`）② 长度 ≥60 字
③ **邻近**（20000 字符内，生成故障成片出现）④ 样板可在 `allowed_repeats` 声明。
按四条在真实站点重测：**0 处** ✓ 判据成立；反例由突变体提供（把一段散文复制到附近 → 精确报出）。

**这条记录本身是台账的价值**：同一个判据"失败一次"不是浪费时间——
它换来了"什么算重复"这个问题的准确定义。

**排序原则**：P1 最便宜且一次覆盖 6 条；P2 覆盖最致命的一类（静默丢内容）；P3/P4 治的是"编造"与"过度自信"；
P9–P13 来自外部调研（第六节），其中 **P9 严重度高且最机械**；P12 要先测量才知道能不能静态判；
P5 需要渲染层，最后做。

## 五、写进每条检查的"发现 → 定位 → 修 → 验证"

这是本域对用户那句原则的实现方式。每条检查失败时输出的**处置卡**必须含：

```
结论     —— 一句话说清"哪里、为什么错"
证据     —— 可复核的依据（逐项列出，不是一句"失败了"）
缺陷所在 —— 生成它的代码/数据位置（file:line），不是产物行号
照着谁改 —— 同仓库里已经做对的那一处（可照抄，不必自己设计）
改法     —— 具体到"改哪个文件的哪几行、加什么"
泛化     —— 这个判据还能往哪扩（教方法，不止修这一处）
验证     —— 一条可执行命令；**重新测量过才算修好**（§十三 第 8 条）
```

**"重新测量才算修好"这一条，本身就是从台账里学来的**：曾经对着未更新的缓存图宣布"已修好"。
所以处置卡的验证字段必须是**命令**，不是"请检查一下"。

## 六、外部调研的增量（2026-10-10 收到的调研包）

**来源**：《纯 Agent 编写交互式教材 · 开发者问题调研报告》（8 类 35 条，自带可信度分层
★一手 / ▲二手 / ●待验证 / ■未覆盖）。原文已逐字复制进本目录：
`外部调研_纯agent教材问题调研_20261010.md`（sha256 前 16 位 `6b976285248982f0`）。

### 6.1 先说这份调研的边界（否则会误用）

1. **它自己标了 ● 级"待验证"的结论不要当事实引用**——例如「多 Agent 故障率 41–86.7%」
   「Agent 编码 token 1000×」都是二手转述、口径不一；原文还明说中文社区未覆盖、
   未做 `web_fetch` 全文抓取、该细分领域"鲜有系统化实证"，结论属**合成性迁移**。
2. **它的多数条目是通用 agent／前端工程问题**（打包签名、token 成本、虚拟滚动、多 Agent 协调），
   并非"教材编写"特有。
3. **它不含我们台账里最疼的那一类**：UI 逻辑不连贯——外壳每页各写一份、注入点落进 `<script>`、
   高亮与页面对不上、滚动被拽回、刷新后状态丢失、折叠按钮消失。那些是**第一手且分辨率更高**的；
   这份调研在相近话题上只到"SPA 路由／可访问性／状态管理"的抽象层。

**结论：它是有用的外部佐证与补盲，不替代第一手台账。**

### 6.3 这份调研里**引擎天然管不了**的部分（如实划线）

调研按"严重度"排在前面的条目里，有相当一部分**不是产物不变量**，塞进引擎会稀释立意
（这是**判定引擎**，不是项目管理器）：

| 调研条目 | 为什么不进引擎 | 该归哪 |
|---|---|---|
| 4.1 越界改动、不读就猜、误用工具删文件 | 这是 **agent 行为**，不是产物里看得见的性质 | 给 agent 的纪律（最小破坏、只改被指示处） |
| 5.1 多 Agent 协调失败（规范/契约/所有权） | 同上，且其数字本身待验证 | 多 agent 编排层的契约设计 |
| 7.1 / 7.2 token 成本、无上限支出 | 与内容正确性无关 | 成本护栏（任务分层、预算上限） |
| 1.5 / 4.3 打包签名、公证、自动更新 | 交付流水线问题 | 发布工程 |
| 5.2 人工审核不足 | 引擎能做的是**把"需人看"显式标出来**（P4 证据类型），而不是替代人工 | P4 |
| 8.1 版权归属不确定 | 法律问题 | 政策与合同 |

**一句话**：能进引擎的标准是「**产物里看得见、且能被证伪的不变量**」。按这个标准筛，
这份 35 条调研里符合的约 10 条（6.2 那张表），其余归别处——**这个筛选本身就是引擎立意的守门人**。

## 七、这份台账自己的规矩

1. **每条都要能证伪**：写不成"改一个已知坏例、它必须变红"的条目，不许进第四节充数；
2. **症状会变、病因不变**：新增条目时先问"它属于 M1–M6 里的哪一条"——归不进去的，可能是个新病因，
   那才值得单独加检查；
3. **同一个问题第三次出现时**，该问的不是"再修一次"，而是"**这个功能还该不该存在**"
   （台账第十二节的原话；那一次用户的答案是：废掉图解）；
4. **本文件不记具体教学内容**，只记机制与判据。

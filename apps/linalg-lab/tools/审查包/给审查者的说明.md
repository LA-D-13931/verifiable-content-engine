# 供审查：可验证的交互式教学内容引擎

**这份说明是给你的路线图。** 请先读它，再决定看哪些文件。
代码总量约 7000 行（引擎 2000 + 工具 5000），不必全读。

---

## 一、这个项目声称做了什么（请重点审这五条）

一句话：**在教学内容发布之前，自动判定「这道学习任务做不做得出来」和
「作者的判题规则判得对不对」。**

它针对的缺陷是这一类——**页面显示、操作反馈、提示文本全都正常，
但其中某个学习任务在任何操作下都不可能完成**。作者（人或模型）通常发现不了。

| # | 可检验的主张 | 证据在哪 | 怎么复现 |
|---|---|---|---|
| 1 | 引擎能在**无浏览器**环境下独立跑完全部任务 | `apps/linalg-lab/tools/verify-engine.mjs` | `node tools/verify-engine.mjs` |
| 2 | 每个判题类型判不过时**必须给出原因与证书** | `verify-diagnostics.mjs`、`audit-coverage.mjs` | `node tools/verify-diagnostics.mjs` |
| 3 | 诊断所指的失败条件**就是真正拦截判定的那一条** | `verify-diagnosis-accuracy.mjs` | `node tools/verify-diagnosis-accuracy.mjs` |
| 4 | 新增一个科目**不需要改引擎层** | `verify-calculus.mjs` | `node tools/verify-calculus.mjs` |
| 5 | 领域插件**不依赖全局、边界干净、缺字段不崩** | `verify-plugin-api.mjs` | `node tools/verify-plugin-api.mjs` |

**建议的质疑姿势**：不要只看测试是否通过——**看测试本身是否在自欺**。
例如第 3 条，它的做法是构造「只触发某一条失败条件」的输入，再检查诊断文本
指向那一条。请审：**这个构造真的只触发了一条吗？**（我们在写这条检查时，
自己就先犯了两次错，见文件头注释。）

## 二、架构（读这一节能省下大量时间）

```
engine-core/                      引擎本体（约 2000 行，纯逻辑）
├─ registry.js                    引擎层：7 个「领域无关」判题类型
├─ mat.js / mat.py                矩阵原语（js 由 py 生成，两侧同源）
├─ mat-vectors.json               77 组共享向量，两侧各自自检
├─ domains/linalg/judge.js        线代领域插件：13 个类型
├─ domains/calculus/judge.js      高数领域插件：4 个类型
└─ adapters/static-content/       第二个领域：静态站点内容一致性校验

apps/linalg-lab/                  参考实现（引擎的一个消费者）
├─ assets/js/labs.json            58 个实验 / 168 个任务（内容，纯 JSON）
├─ assets/js/*.js                 画布、交互、界面（约 2200 行）
└─ tools/                         校验与生成工具（约 5000 行）
```

**核心设计主张：两级分派 + 一条可检验的分界线。**

| 判据里出现…… | 放在哪一层 |
|---|---|
| 「秩、行列式、特征值、列空间」等**学科概念** | `domains/<科目>/` |
| 只是「数值相等 / 位置命中 / 序列匹配」 | `registry.js` |

**这条分界线的可检验后果**：新增科目时 `registry.js` 与 `mat.js` 一行都不用改。
高数科目就是这么接进来的（`domains/calculus/judge.js`，320 行）。

**每个判题返回三元组** `{ pass, reason, certificate }`：
- `reason` 是给人看的一句话原因
- `certificate` 是**判定依据（见证或反证）**，**可被独立复核**

## 三、请重点审的六处（我们自认为最可能有问题的地方）

1. **`engine-core/domains/linalg/judge.js` 的 `DIAGNOSE` 表**
   判定分支有的有 4 条失败条件，而诊断是按条件逐条写的。
   请审：**诊断的条件顺序是否与判定的返回顺序严格一致？**
   不一致会导致「诊断说的原因不是真正卡住的那一条」——这个缺陷我们出现过一次。

2. **`verify-diagnosis-accuracy.mjs` 的测试构造**
   它声称「只触发一条失败条件」。请独立核算那几个输入是否真的只触发一条。

3. **`verify-static-adapter.py` 的差分对照**
   它证明「迁移后的适配器与迁移前的原脚本结论一致」。
   请审：**它比的对不对？有没有把不该算的算成一致？**
   （原脚本不在本包里，属主站；见第六节。）

4. **`verify-plugin-api.mjs` 的「不依赖全局」检查**
   它用正则扫描源码。请审：**这个正则会漏报或误报吗？**
   （第一版用裸子串 `sk-` 做凭据扫描，结果 `task-`、`risk-` 全被误报。）

5. **矩阵原语的两侧同源**
   `mat.py` 是权威实现，`mat.js` 由它生成。请审：
   **生成的 js 是否真的等价于 py？** 77 组向量够不够覆盖边界？

6. **`packaging` 与静态适配器的「跳过」语义**
   宿主站点没提供某脚本时，检查返回「跳过」而不是「失败」。
   请审：**这个设计会不会掩盖真问题？**（即：本该失败却被当成跳过）

## 四、怎么跑起来

**零第三方依赖**，只要 Node 与 Python 3：

```bash
cd <解压后的目录>

# 五项离线自检（不需要浏览器）
node apps/linalg-lab/tools/verify-engine.mjs
node apps/linalg-lab/tools/verify-registry.mjs
node apps/linalg-lab/tools/verify-calculus.mjs
node apps/linalg-lab/tools/verify-diagnostics.mjs
node apps/linalg-lab/tools/verify-diagnosis-accuracy.mjs
node apps/linalg-lab/tools/verify-plugin-api.mjs
node apps/linalg-lab/tools/audit-coverage.mjs

# 静态内容适配器（需要一个站点目录；本包内用 apps/linalg-lab 代替）
python3 engine-core/adapters/static-content/verify.py apps/linalg-lab --allow-outside
```

**浏览器类的三项**（`verify-themes` / `verify-actions` / `smoke`）需要
`puppeteer-core` 与 Edge/Chrome，**本包未附带 node_modules**，
所以它们跑不了——这**不影响**上面这些核心主张的验证。

## 六、本包不含什么（以及为什么）

| 不含 | 原因 |
|---|---|
| 主站（高数学习站）与它的校验脚本 | 属另一条工作线；静态适配器有 2 项是**委托**它的脚本执行的，故本包里这两项会显示「跳过」 |
| `node_modules` | 依赖，浏览器类工具需要，核心主张不需要 |
| git 历史与 27 个回滚标签 | 本包是快照 |
| 真实题库的答案键 | 保密材料 |

## 七、已知的局限（我们主动列出，请一并审是否诚实）

1. **必要性而非充分性**：合格 ⊢ 任务可完成且判据自洽；
   合格 ⇏ 教学有效、难度合适、学生看得懂。这是**发布前的门禁**，
   不是教学质量的裁判。
2. **不验教学意图**：作者意图没有被形式化，我们不声称能验证它。
3. **判定策略是封闭集合**：能验的类别可枚举，其余明确不验。
4. **不做形式化证明**：这是工程判定策略，不提供定理级证明。
5. **不含渲染层**：引擎只判题、不画图。
6. **静态适配器有两项尚未接进规则层**：结构与双语检查目前**委托**原脚本执行、
   只解析其结论（见 `engine-core/adapters/static-content/README.md`）。
   这是刻意取舍（不重写已验证的资产），但**不能算作「已迁移」**。
7. **「最有利上下文」有个已知盲点**：它为每个任务构造最有利状态。
   如果作者把判据写成**恒真**（任何状态都通过），这个模式查不出来。
   我们**没有**解决这个问题——请审这是否是可接受的范围界定。
8. **可视化页的样例**是人工构造的，不是真实语料。
   真实缺陷只有 4 例（写在 `verify-registry.mjs` 的回归用例里）。
